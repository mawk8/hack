# Этап 1: данные, правила и проверяемые гипотезы

Статус: техническая подготовка пакетов A, B и C выполнена и независимо проверена. Человеческая проверка меток и ответы организаторов ожидаются. Это план аналитической подготовки, не разрешение писать приложение или запускать платные эксперименты.

**Цель:** получить проверяемый контракт данных и протокол оценки, по которому можно честно сравнить первый прототип и улучшения.

**Архитектура работы:** один исполнитель готовит результат; независимый проверяющий воспроизводит существенные проверки; ведущий сопоставляет результат с гипотезой и критериями приёмки. Проверяющий не принимает работу только по отчёту исполнителя.

**Инструменты:** локальное чтение ZIP/JSONL/Parquet, доступный совместимый Python, Markdown и JSONL для результатов. Без нового агентного фреймворка, серверов и базы данных.

**Основание:** `output/pdf/avito_hackathon_report.pdf`, постановка и справочник внутри архива `C:/Users/Admin/Downloads/innoglobalhack_avito(1).zip`, согласованные ограничения пользователя.

## 1. Границы

- Читать исходный архив без изменения. Все создаваемые материалы — внутри `E:/hackaton`; без удаления данных, кешей и дублей.
- Не менять Anaconda и глобальные настройки. Сначала проверить существующие совместимые средства чтения Parquet. Если их нет — описать конкретную зависимость и остановить только зависимую часть; установку согласовать отдельно.
- Не обучать модели, не создавать UI, не отправлять объявления во внешние API и не расходовать API-бюджет на этом этапе.
- Не считать автоматические метки правильными по умолчанию. Ответы агентов не называть человеческой разметкой.
- Не использовать public-test для настройки до подтверждения его назначения организаторами.

## 2. Роли и обязательный цикл

1. **Ведущий:** формулирует гипотезу, проверку, ограничения и критерий решения до начала работы.
2. **Исполнитель:** получает только задачу, пути источников и нужный раздел этого ТЗ; выполняет чтение и анализ, сохраняет результат и воспроизводимый способ проверки.
3. **Проверяющий:** получает тот же контракт и результат без всей истории чата; независимо проверяет исходные данные и расчёты. Возвращает конкретное замечание, доказательство, существенность и минимальное исправление.
4. **Ведущий:** принимает или отклоняет каждое замечание с основанием. При существенном дефекте исполнитель исправляет, проверяющий перепроверяет затронутый результат.
5. **Решение:** «принято», «опровергнуто» или «недостаточно данных». Отсутствие замечаний агента само по себе не доказывает корректность.

На одном пакете работают исполнитель и затем проверяющий, а не два параллельных автора одного решения. Два цикла исправлений — ориентир; если дефект остаётся, фиксируем блокер и меняем подход, а не автоматически принимаем результат.

## 6. Superpowers, Ponytail и плагины

- Superpowers writing-plans используется для этого ТЗ. При выполнении использовать subagent-driven-development для ограниченных пакетов и независимой проверки; при конкретном сбое — systematic-debugging; перед заявлением о завершении — verification-before-completion.
- Не запускать все навыки на каждый шаг. Полный повтор процесса для форматирования текста или исправления опечатки не нужен.
- Ponytail применяется после проверки требований: убрать лишние зависимости, агентные стадии и абстракции. Он не разрешает сокращать обязательную оценку, удалять файлы или игнорировать критерии задачи.
- Новые плагины не устанавливать без конкретного пробела. Context7 нужен при работе с незнакомым API библиотеки; дополнительный доступ к документации OpenAI — при соответствующей реализации. Сейчас необходимые чтение, поиск и агенты доступны.

## 7. Переход к прототипу

Ориентир аналитического этапа — до 3 часов работы агентов и 1–2 часов команды на ручную проверку, частично параллельно. Это плановая оценка. Если лимит исчерпан, фиксировать выполненное и блокеры; не превращать подготовку в бесконечную настройку инструментов.

Этап принят, когда завершён аудит, подготовлены контрольные группы и протокол, существенные замечания проверяющего закрыты. Человеческая проверка меток и ответы организаторов отмечаются отдельно: агент не может закрыть их за людей.

Если часть ответов ещё ожидается, допустим ограниченный baseline на явно зафиксированных допущениях после поручения пользователя перейти к прототипу. Его результат нельзя выдавать за подтверждённое качество финального решения.
