# Актуальный план MVP

Обновлено 15.11.2026. Этот документ заменяет прежние планы для дальнейшей работы. Код: ветка `prototype`.

**Новое решение пользователя, 15.11:** финальным выбран внешний [CaneRig/avihack](https://github.com/CaneRig/avihack), master. Пользователь сообщил F1 0,95 для полученной отправки. Локальный prototype сохраняется; незавершённые ниже работы по Qwen не являются подтверждённой архитектурой финальной отправки. Текущий приоритет — разбор готовых черновиков и защита.

## Цель и ограничения

- Входные объявления всегда из 101; предсказываем 102–106. В интерфейсе source фиксирован, совместимость API сохраняем.
- Оценка 5/3/2: классификация, работоспособность, черновики. Черновики не публикуются автоматически.
- Срок по записи ментора:16 ноября 08:00; точное время/часовой пояс и правила private-submit подтвердить в чате организаторов.
- Public разрешён для настройки. Контроль не используем для выбора промпта/порогов. Исходные метки шумные.
- Сейчас приоритет — полный MVP. Массовую синтетику и дообучение LLM отложить; существующие инструменты сохранить.
- Уточнение по полному диалогу ментора, принято пользователем 15.11: явно доступная только внутри комплексного ремонта работа не получает отдельной категории/черновика. Само «под ключ» не означает запрет отдельных работ. Собственная бригада/делегирование не исключает предлагаемую услугу; чужие услуги, отрицания и поиск исполнителей исключаются.
- Новый пользовательский сценарий: текст → LLM обнаруживает категории с цитатами → пользователь отмечает интересующие → LLM создаёт только выбранные черновики. F1 считается по автоматическому обнаружению до выбора пользователя.

## Исполнение уточнённого сценария, 15.11

Оркестратор принимает работы поэтапно; исполнители и проверяющие — GPT-6.1 Sol / medium с отдельным коротким контекстом. Общая ветка prototype, отдельные области файлов, без самостоятельных commit/push агентов. Оркестратор проверяет результат, возвращает замечания исполнителю, затем делает scoped commit/push. Без скачивания LLM/runtime, платных API и настройки по control/human40.

1. **Готово: код и synthetic-проверки — правила и API.** В `avito/llm.py` отдельное обнаружение без title/text; общая предметная инструкция с пакетными/партнёрскими правилами. `POST /detect` принимает `{description,mcId}`, возвращает `{categories:[{mcId,evidence,constraints}],meta}`. `POST /generate` принимает `{description,mcId,selected_mcIds}`, возвращает прежний диагностический `{result:{drafts},evidence,meta}` с ровно выбранными категориями либо явной ошибкой. Пустой выбор — локальный пустой результат без LLM. Прежние /predict и /analyze остаются совместимы. Исходный текст повторно передаётся генератору; выбор не разрешает выдумывать услуги. Проверки JSON, точных цитат, source/повторов, незавершённых ответов, тайм-аутов, lock и busy сохраняются. Приёмка: целевые synthetic HTTP-тесты и полный unittest.
2. **Готово: код и synthetic-проверки — UI и CSV.** Две кнопки: «Найти услуги» и «Создать черновики»; категории с цитатами, изначально без галочек. При правке текста сбрасываются обнаружение, выбор и черновики; без выбора генерация недоступна. Для CSV: UTF-8/BOM, запятая/точка с запятой/табуляция, обязательный description, optional testcase (официальный идентификатор), id/title; title показывается, description остаётся входом модели. Отсутствующий id — номер строки; повторяющийся id — ошибка импорта. Не более 200 строк и 2 MiB. Парсинг стандартным csv на backend, последовательные вызовы /detect по строкам с прогрессом, выбор категорий отдельно на каждую строку, затем /generate. Ошибки строк сохраняются отдельно от истинно пустых результатов; JSON-экспорт содержит id, автоматические категории, выбор, черновики и ошибку. Автоматические категории не затираются выбором. Без очередей/БД/публичных туннелей. Приёмка: CSV-тесты, browser smoke на синтетике и полный unittest.
3. **Готово: ограниченный silver-пересмотр — адресная проверка данных.** Не менять frozen v2/train/control/human40. На public подготовить новую версию правил и проверить прежний silver-пилот20 плюс очередь13 конфликтов по пакетным/партнёрским ограничениям; сохранять отдельный overlay с цитатами/неопределённостью, статус silver_provisional, без human_verified. Повторяющиеся тексты проверять один раз. Не расширять на весь public/train автоматически. Проверять schema/ID/хэш/цитаты и не интерпретировать согласие как accuracy. Если прежний пилот меняется, сохранить обе версии. После этого — решение о расширении, а не массовая переразметка.
4. **Внешняя зависимость — реальная LLM.** После доступности 3060 измерить отдельно detection/generation и полный сценарий, фактичность, ошибки и время; пока фиксировать только synthetic-проверки. Правила/количество/private-submit уточняются у организаторов, публичность GitHub автоматически не менять.

От товарища берём идеи словесных признаков, нормализации, анализа ошибок и гибрида. Не переносим агрессивное отрезание SEO-хвоста, проверяющий с одобрением при сбое, произвольный fallback-текст или некалиброванные веса 50/50 как готовое решение. Полные замеры включают генерацию/сбои/повторы; кэшированные ответы не считать онлайн-скоростью.

## Как работать с планом

1. Взять ближайшую незавершённую задачу. Прочитать только связанный код и STATUS.md.
2. Перед опытом записать гипотезу, версии данных/модели/промпта и изменяемую переменную.
3. Выполнить небольшую законченную часть; проверить сценарий и существенные ошибки. Использовать Ponytail для простоты, Superpowers для исполнения/review по необходимости.
4. Получить независимую проверку существенного изменения; исправить подтверждённые замечания.
5. В STATUS.md записать результат, команду/артефакт и ограничение; обновить статус строки здесь, сделать scoped commit и push в prototype.
6. При изменении требований обновить этот план, а не создавать очередную параллельную версию.
